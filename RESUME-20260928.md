## Where the DSP stands (to pick it up again)

- Re-enable: remove `NEXT_NO_DSP` from NeXT-Color.qsf, build, and install a
  Main from next-color 35cfed3 or later.
- Last DSP builds: FPGA 65b3d6d seed 5 (timing met +0.106 / +0.224,
  `scratch/rbf/NeXT-Color_65b3d6d_seed5_dd8b8c4d.rbf`); Main 35cfed3 =
  `scratch/MiSTer_5047bec9` (+ .elf: dsp_core 0x00163aa0, dsp_ram 0x0103acd0
  for coredump).
- Works: sound through the DSP (sndplay mono / mu-law), `playscore -w` of
  CoventryCarol (47 s), Examp1 (bit-identical across Mains), Examp3.
  Hangs: BachFugue (44.1 kHz), Twilight, Jungle -- NeXTSTEP's sound driver
  resets the DSP when its queue waits at a DMA buffer end.
- The mechanism (mach_kernel, disassembled from the disk's /mach_kernel m68k
  slice with symbols: `scratch/mk/kernel.dis`, DSP driver part `kdsp.dis`):
  - dsp_dev_loop 0408f84c; DSP interrupt handler 0408f6dc -- with DMA state
    ($40c7f42) == 3 it calls dsp_dev_reset_chip (0408f7b2).
  - DMA read buffer end (04090be2): state = 3, queue [wait HC 0][HC $12
    HOST_R_DONE][wait HC 0][ICR = ICR & ~$73 | $81 (INIT RX)][state 0], run
    the queue.  If anything ahead in the queue waits (a host message on
    TXDE, TRDY, HF2/HF3), state 3 persists and the next DSP interrupt (RREQ
    + the garbage word in RX, or TXDE) resets the DSP.
  - dspq_enqueue inserts by priority (DMA ops 0 < untimed 1 < timed 2) but
    not ahead of a message already under way; dspq_check (040918a6) sets
    TREQ and returns when TXDE is 0; the data op polls TXDE 50 x delay(2).
  - RX words are read only while the user's DSP-message buffer has room
    ($40c7f26 / end $40c7f22); $05 (HOST_R_REQ) sets state 1, any other word
    goes to the user; a full buffer turns RREQ off.
- Fixed (all bench-tested in tb_tc_dsp, each case failing on the old code):
  the ack order (Main 07e9c29: a command's handler runs before the host's
  next access, so the INIT flushes the HOST_R_DONE ack); TRDY once the
  words are on the link + HF3 alone while a command runs (FPGA 65b3d6d +
  Main b06902a cvr_wait); host words acknowledged when queued (Main 35cfed3).
- Left:
  1. TXDE still dips while more than K_TX = 2 host words await the ARM's
     acknowledgement (the DSP thread on core 0 can stall ~0.2 ms; D2H is
     published at the end of a slice).  Fix: K_TX ~64 in tc_dsp (tx_out
     wider), Main's ack margin LINK_TXQ - K_TX - 2.  One FPGA build.
  2. A command's handler takes ~0.1-2 ms here (a few us on a 56001); while
     it runs (hc_pend, HF3 shown) the driver's next host message waits, and
     a buffer end in that window resets the DSP.  Needs a faster DSP (the
     interpreter at 1.5 M instr/s; gprof: 56-bit ALU, parallel moves, AGU,
     dispatch -- `scratch/dspbench/`), or a DSP in the FPGA (FPGA ~93%).
  3. Not tried: live `playscore`, Gamelan, the CD's Music Kit apps.
- Tools: `scratch/dspbench/ringmon SECS [f]` (on the MiSTer: timestamped
  control messages; block-buffered, the tail flushes at exit), `ring_dump.py`
  (last 256 each way), `coredump` + `dsp_state`, `scratch/snd_pull.py`
  (a .snd off the disk image -> WAV; MSYS_NO_PATHCONV=1), `scratch/mk/`
  (monitor symbols, the MK 5.6.2 source from NeXTSTEP-Apps3.iso, kernel
  disassembly, ring logs of every run).
- Gotchas: `type_text.py "" ENTER` types a space (log in with `ENTER` alone);
  guest_click.py takes `MASK=x0,y0,x1,y1` to ignore a blinking caret; csh
  aborts the rest of a `;` line on Ctrl-C.
